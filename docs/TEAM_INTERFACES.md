# Интерфейсы первой волны — v1

Общий вход для TASK1–TASK7. Это публичный контракт модулей, не журнал работы.
Перечисленные выходы ещё предстоит реализовать.

## Работа и приёмка

- У каждого свой клон/ветка. PR меняет только область своей задачи.
  Общие контракты и загрузчики интегрирует ведущий; TASK5 может минимально
  изменить `gateway/auth_gate.py` для lifecycle/независимой отправки.
- Результат на 2–3 дня — рабочий первый инкремент. К концу первого дня
  приложить минимальный артефакт или сообщить о блокере.
- В PR: команда запуска, тесты, версия FG/ОС, ограничения. XML/Python,
  loopback, FGMS и реальные FG-клиенты — отдельные уровни проверки.
- Не менять чужую инфраструктуру, личные настройки и сторонние исходники
  без согласованного задания. Не включать секреты и личные журналы в PR.

## Геометрия и физика

- Пакеты: `Aircraft/sa_xwing/`, `Aircraft/sa_tie/`, `Aircraft/sa_fdm_lab/`.
  Просмотр без FDM не означает успешного полёта.
- Сцена TASK4: `scenery/space_arena/`, её `manifest.json` описывает
  координаты/позы/трансформации. Это формат проекта, не штатный формат FG:
  пакет сопровождается инструкцией установки/загрузки.
- Метры. Описать начало координат, нос/верх и преобразование в FG;
  не смешивать оси aircraft-body, модельного файла и экспортера.
- Runtime: `.ac` + XML-обёртка, текстуры с относительными путями.
  Первоначальный бюджет — до 25k треугольников вместе с кабиной и до 2K
  текстуры; это рабочий лимит, не гарантия FPS.
- Узлы: `hull`, `cockpit`, `engine-1..N`, `muzzle-1..N`, для X-wing
  `sfoil-1..4`. Точка глаз/опоры/выходы — в локальных метрах в README.
- Входы тестовой анимации: `/sim/space-arena/visual/throttle` (0..1),
  `/sim/space-arena/visual/foils-open` (bool). Позже подключается адаптер
  фактических органов управления. Эффекты не подтверждают урон.
- Своя геометрия или разрешённый ресурс. Автор/источник/лицензия/хеш
  оригинала обязательны; оригиналы не перезаписывать конвертацией.
  Полный FGData, кеш сцены и экспортные резервные копии в Git не добавлять.

## Клиент, транспорт и матч

- Фракции: `rebels`, `empire`; первые ship IDs: `xwing`, `tie`.
  Не занимать произвольные generic MP slots зависимости и не вводить
  wire-протокол без отдельного контракта.
- FGMS пересылает движение, gateway проверяет доступ/переносит датаграммы.
  Общий счёт и бюджет — отдельная ответственность match-компонента.
- UI выдаёт намерение `team_id`, `ship_id`; право на spawn подтверждается
  авторитетным компонентом. Callsign не стабильный player ID.
  Mock-ответы явно обозначаются, не показываются как реальная сеть.
- TASK7: offline-состояние/события версии `1` с `match_id`, `player_id`,
  `spawn_id`, `event_id`. Модель событий и примеры принадлежат TASK7;
  до интеграции UI пользуется mock-адаптером. На wire их пока не отправлять.
- Цель 15 подтверждённых уничтожений врага. Один активный аппарат, один
  слот на каждый конкретный тип своей фракции за матч; начальное появление
  расходует слот. Reconnect/новый callsign не возвращают слоты.
- Команда фиксируется на раунд, friendly fire off, смерть учитывается
  один раз по spawn_id. Fallback малых составов — в TEAM_PLAN.

CI и выбор runtime-авторитета относятся к интеграционному контуру;
они не реализуются автоматически выполнением транспортной задачи.
