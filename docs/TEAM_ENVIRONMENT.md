# Подготовка окружения разработчика

## Требуется

- Git и собственный клон командного репозитория.
- Python **3.14** для воспроизводимой тестовой отправной точки.
  Другие версии проверяются отдельно; переносимость не следует из синтаксиса.
- Для моделей/клиента/FDM: **FlightGear 2024.1.4 + FGData 2024.1.4**,
  c172p и одинаковая доступная тестовая scenery (например KSFO).
- Docker/Compose нужен только для настоящих FGMS smoke-тестов и deployment;
  Python-тесты не требуют Docker. Для native FDM — инструменты выбранного
  backend, для визуальной приёмки — рабочая графическая среда.

FlightGear устанавливается **отдельно**, не в Git. `fgfs` может быть в PATH
или задаваться полным путём через `tools/launch.py --fgfs`.
Личные пути и endpoint сохраняются только в локальном профиле.

## Python

Из корня проекта:

```sh
python -m venv .venv
```

Активировать окружение:
- Linux/macOS: `source .venv/bin/activate`
- Windows PowerShell: `.venv\Scripts\Activate.ps1`

```sh
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tools -p "test_*.py"
python tools/launch.py --dry-run
```

`--dry-run` не запускает FG и не устанавливает соединение. Реальный solo-
старт: `python tools/launch.py --fgfs /path/to/fgfs`. Если FG не найден,
указать путь к локальной установке, не коммитить свой профиль.
Пример профиля: `client/client.example.json`; локальная копия:
`client/local.json` (исключена из Git).

## Уровни проверки

1. Unittest/XML/конфиги.
2. Реальные loopback TLS/WebSocket/UDP проверки, если реализованы.
3. Настоящий FGMS и изоляция его портов.
4. FlightGear: просмотр модели/кабина, native FDM, полёт.
5. Два клиента в обе стороны, затем общий матч нескольких игроков.

В PR указывать реально пройденные уровни, версии ОС/FG и команду воспроизведения.
Не объявлять Windows/macOS/Linux или Docker проверенными по одному Python-
прогону. Linux-бинарники разных дистрибутивов могут требовать несовместимые
libc/графические зависимости; headless не заменяет визуальное испытание.

Для удалённых игровых тестов администратор предоставляет TLS endpoint и
личное приглашение. Админские SSH/API-ключи разработчикам и агентам для
обычной работы не нужны. Не передавать секреты через Git/PR/логи.
