# Следующий этап gateway: MP-датаграммы и backend UDP

Это исследование pinned исходников, не уже реализованный relay и не приёмка
FlightGear. Текущий отдельный spike ограничен TLS/auth, без UDP backend.

## Размер и границы

Оба pinned endpoint используют MAX_PACKET_SIZE=1200. Ограничение WebSocket
4096 в TLS-spike — только его тестовая граница, не размер FG-пакета.
UDP-relay должен сверить реальные пакетные границы/MsgLen и более строгий
предел до отправки FGMS. Одна WS binary-message = одна датаграмма;
не сливать сообщения и не использовать TCP stream без framing.

T_MsgHdr содержит шесть XDR uint32 и 8 байт Name (полный header=32 байта).
Magic клиента — FGFS (0x46474653), protocol 1.1 (0x00010001). Внутренний
relay magic не принимать от обычного клиента. Разрешённые MsgId задавать
по pinned FG-клиенту, не пропускать произвольные команды.

Перед отправкой backend проверять полный header, MsgLen против фактической
длины, кодировку/завершение callsign и соответствие identity приглашения.
Имя соединения или прошедший TLS сами по себе не запрещают подмену callsign.
Бюджет/фракцию нельзя брать из непроверенного имени в payload.

Не переносить C++ sizeof position-структур в Python наугад: копии
mpmessages.hxx в старом FGMS и актуальном FG могут отличаться padding и
эволюцией полей. На relay-этапе содержимое позиции/свойств остаётся opaque;
полный codec для авторитетного матча потребует отдельного source review.

## Адреса и обратный поток

ReplyPort в header deprecated и клиент выставляет 0. В pinned FlightGear
один mSocket привязывается к rxaddress/rxport и используется для sendto.
NAT вне клиента может менять наблюдаемый сервером source-port; возможность
обратного потока необходимо проверять на целевом маршруте.

FGMS хранит Address фактического отправителя и отправляет данные обратно
на него. Gateway нужен отдельный устойчивый UDP endpoint на identity,
чтобы не смешать клиентов на одном socket. Backend destination фиксируется
конфигурацией, а не принимается из WS-сообщения/URL пользователя.

Клиентский local bridge слушает только loopback и доставляет ответы в
согласованный local FG receive endpoint. Никакой LAN-публикации companion.
Точную адресацию и наблюдаемость обеих сторон проверить реальными клиентами.

## Reconnect — не просто открыть новый socket

FGMS сначала ищет игрока по callsign, а при несовпадении source Address
отбрасывает обновление. Новый backend source-port при быстром reconnect
может конфликтовать со старой записью до playerexpires (сейчас 10s).

Следовательно, до рабочего relay нужна явная политика backend endpoint:
ограниченная lease/grace привязка к identity либо иной проверенный механизм
удаления/истечения старой записи. Не публиковать telnet/admin ради обхода.
Grace нельзя превращать в новые жизни, неограниченные сокеты или выдачу
сообщений уже отозванному соединению. Все лимиты/таймауты должны быть тестируемы.

Просто TCP/TLS echo не проверяет этот случай. Нужны последовательно:
реальные локальные WS+UDP tests, настоящий FGMS, затем два настоящих fgfs.
Изменение HP/счёта/числа появлений в этом транспортном шаге запрещено.
