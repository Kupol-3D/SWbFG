# TASK3 — эксперимент тягового атмосферного полёта

Выбран **JSBSim** в штатном FlightGear **2024.1.7**. Один автономный стенд:
[`Aircraft/sa_fdm_lab`](../Aircraft/sa_fdm_lab/README.md). Цель — проверить
управляемый полёт с явно заданной поддержкой веса, без изменения FG,
сторонних моделей и настроек машины. Все массы/тяги ниже — инженерные
допущения для игрового эксперимента, не сведения о корабле из лора.

## Выбор backend

| Критерий | YASim | JSBSim |
|---|---|---|
| Задание обычного самолёта | Геометрия/режимы, native solver определяет параметры | Явные силы, коэффициенты, масса и инерция |
| Зависание при нулевом набегающем потоке | Требует отдельного физического источника вертикальной тяги; продольного двигателя недостаточно | Штатные `external_reactions` задают силу в LOCAL и моменты в BODY |
| Проверяемость допущений стенда | Подгонка самолётного solver под несуществующий аппарат не отвечает на вопрос о repulsor | Каждая сила/момент и насыщение видны в XML; native загрузка и численное интегрирование |
| Цена первого эксперимента | Понадобится придумывать аэродинамическую геометрию и solve-режимы | Достаточно одной модели без подъёмных поверхностей |

Это сравнение возможностей, а не две реализованные FDM. YASim-профиль и
YASim solve не создавались. JSBSim не требует отдельного офлайн-подбора
коэффициентов: выполнены нативная загрузка/интегрирование, затем настоящий FG.
API проверен по установленным исходникам, а не только по текущей web-версии:
`src/FDM/JSBSim/models/FGExternalForce.cpp`, `FGMassBalance.cpp`,
`models/flight_control/FGFCSFunction.cpp`, интеграция `JSBSim.cxx`.
Общая документация: [JSBSim external forces](https://jsbsim-team.github.io/jsbsim/classJSBSim_1_1FGExternalForce.html),
[FCS gain/ограничители](https://jsbsim-team.github.io/jsbsim/classJSBSim_1_1FGGain.html).

## Механика и вымышленный помощник

Обычная механика: масса/тензор инерции, гравитация и вращение Земли JSBSim,
интегрирование положения и скоростей, продольная приложенная тяга. Сопротивление
в спокойном воздухе приближено квадратичной силой по продольной оси:
`D = 0.5*rho*CdA*u*abs(u)`. Подъёмных поверхностей нет. Поперечная и
вертикальная аэродинамика, сваливание и точные коэффициенты аппарата не заявлены.

Вымысел: независимая от ориентации корпуса вертикальная сила в LOCAL,
компенсирующая вес, автомат удержания высоты, активные моменты стабилизации,
боковое демпфирование и реверсивное торможение. Источник энергии/расход топлива
не моделируются. Без этих сил стенд не является летающим самолётом.
Особенно боковое демпфирование при повороте требует тяги: это не бесплатная
аэродинамическая возможность корпуса на нулевой скорости.

| Параметр | Значение и единицы |
|---|---|
| Масса, постоянная | 1000 kg; топливо/смена массы отсутствуют |
| Ixx / Iyy / Izz | 1200 / 2500 / 3000 kg·m²; CG в нуле, произведения инерции 0 |
| Продольная тяга | 0..8000 N, команда 0..1 |
| `CdA` | 1.3 m²; используется плотность атмосферы JSBSim |
| Торможение | `−1.5*m*brake*u`, постоянная времени около 0.667 s |
| Суммарная продольная сила | насыщение −20000..+8000 N |
| Боковой помощник | `−m*v/1s`, насыщение ±12000 N |
| Repulsor | `m*clip(g0+0.8*(h_cmd−h)+1.8*v_down, 0, 2*g0)` |
| g0 | 32.174 ft/s² ≈ 9.80664 m/s²; насыщение около 19613.3 N |
| Удержание высоты | `h_cmd` по умолчанию 3280.839895 ft (1000 m), PD без интегратора |
| Крен / тангаж | `I*(3*(angle_cmd−angle)−2.8*rate)`, rad/s и rad |
| Команды углов | `phi_cmd=0.25*aileron`, `theta_cmd=−0.17*elevator`, rad |
| Рыскание | `Izz*2*(0.1745329252*yaw−r)`, команда скорости до ±10°/s |
| Моменты помощника | каждый ограничен ±10000 N·m |
| Поддержка/стабилизация | `lab/support`, `lab/stabilize`: штатные значения 0 или 1 |

Продольная тяга и тормоз — одна результирующая сила в CG по BODY +X.
Repulsor приложен в CG по LOCAL −Z (вверх), поэтому поворот аппарата сам
по себе не уменьшает поддержку веса. Боковой помощник по BODY Y создаёт
изменение траектории вслед за поворотом носа. Это аркадная схема управления.
Она не доказывает возможность реализовать аппарат обычными двигателями.

Единицы XML массы/геометрии задаются атрибутами KG, KG*M2, M. Внутренние
функции JSBSim работают в slug, ft, s, lbf, lbf·ft: `1 ft=0.3048 m`,
`1 lbf=4.4482216152605 N`, `1 lbf·ft=1.3558179483314 N·m`.
Коэффициенты переведены в эти единицы; например 8000 N = 1798.47155 lbf.
BODY: нос/право/вниз; LOCAL: север/восток/вниз; structural и визуальная
модель: назад/право/вверх. Полное преобразование AC3D/камер и точки опор
описаны в README пакета. Масса и инерция не вычисляются из greybox-геометрии.

## Инициализация и trim: что не получилось

Обычный самолётный trim при нулевой скорости не подходит этой FDM: он
подбирает alpha/elevator/throttle, но поддержкой высоты управляет собственный
контроллер. Реальный вывод неуспешной попытки сохранён в
[`trim-attempt.txt`](fdm_lab_evidence/trim-attempt.txt). Это отрицательный
результат для **самолётного trim**, а не успешный solve. Его нельзя предъявлять
как подтверждение аэродинамической модели.

В FG 2024.1.7 обнаружена дополнительная особенность `FGJSBsim::init()`:
при `trim=0` позиционные setters из `common_init()` меняют propagated state,
затем `RunIC()` возвращает исходные IC; заданный CLI старт теряется. Запуск
без обхода этой особенности начинался у уровня моря и выходил за режим.
Не меняя движок, пакет после сигнала `fdm-initialized` один раз устанавливает
штатные `ic/*` из presets и вызывает штатный `simulation/reset=1`.
Это обычная инициализация до отсчёта испытания. После неё `tick()` пишет
только команды тяги, тормоза, рыскания, высоты и органов управления;
положение/скорость/ориентацию он не подменяет. Эта же инициализация работает
при ручном запуске. Повторное меню Reset пока не поддерживается.

Самолетный startup trim в итоговой команде выключен. Конструктор FG всё равно
вызывает внутренний пробный `DoTrim()` до размещения аппарата; его результат
не используется стендом и не считается solve. Для JSBSim-профиля приложен
действительный stdout штатной standalone-утилиты и её численные выборки.

## Воспроизведение

Команда реального FG-прогона и отдельный ручной сценарий:
[`Aircraft/sa_fdm_lab/README.md`](../Aircraft/sa_fdm_lab/README.md).
Автоматизированный маршрут выполняет:

| Время от старта измерений | Команды |
|---|---|
| 0–30 s | Зависание; на 10–15 s aileron=0.4/elevator=−0.3, затем отпускание |
| 30–50 s | Малая тяга 0.02, тормоз отпущен |
| 50–75 s | Разгон с тягой 0.12 |
| 75–90 s | Тяга 0, активный тормоз 1 |
| 90–115 s | Разворот к 180° на малой скорости |
| 115–180 s | Возврат к начальным координатам, ограничение скорости 25 m/s; остановка при дистанции <5 m |
| 155–170 s | Дополнительно команда набора +50 ft (15.24 m) и возврат высоты |
| До ≥205 s | Зависание; итоговая запись и штатный выход FG |

Телеметрия берётся из **реальных свойств FG/JSBSim** раз в ~1 s;
интегрирование FDM не заменяется Python. Возврат использует координаты;
`north_m/east_m` — локальная сферическая оценка относительно старта
(дистанции сотни метров, это не геодезическая навигация). Положения не пишутся.
Скорость — FG `airspeed-kt`, переведённая в m/s; на вертикальном манёвре она
включает вертикальную составляющую. Полное поле `support_lbf` показывает силу.

Нативная проверка JSBSim воспроизводится вне репозитория. Временный корень
содержит ссылку `aircraft` на каталог `Aircraft` проекта; это учитывает
чувствительность к регистру на Linux. Например в POSIX shell:

```sh
LAB_REPO="$PWD"
LAB_NATIVE_DIR="$(mktemp -d)"
ln -s "$LAB_REPO/Aircraft" "$LAB_NATIVE_DIR/aircraft"
cd "$LAB_NATIVE_DIR"
/path/to/JSBSim --root="$LAB_NATIVE_DIR" --aircraft=sa_fdm_lab \
  --initfile=reset00 --end=205 --simulation-rate=120 --nohighlight \
  --logdirectivefile="$LAB_REPO/Aircraft/sa_fdm_lab/Scripts/output.xml"
# Контрольный опыт, отдельный новый каталог результата:
# --script="$LAB_REPO/Aircraft/sa_fdm_lab/Scripts/no-support.xml"
# вместо --aircraft/--initfile/--end/--simulation-rate.
```

В локальной macOS-сборке standalone JSBSim требует
`DYLD_LIBRARY_PATH=/path/to/FlightGear.app/Contents/Frameworks`: без этого dyld
не находит `libcares.2.dylib`. Библиотеки/бинарники не патчились и не копировались.
Абсолютный `--outputlogfile` в этой сборке неправильно дописывается к root;
использовано относительное имя из `Scripts/output.xml`.

## Измерения и границы вывода

**Результат: технический GO для продолжения атмосферного прототипа с явно
вымышленным помощником.** Ведущий принимает окончательный go/no-go с учётом
описанных ограничений. Обычная продольная тяга без поддержки веса этот
результат не обеспечивает.

Реальный оконный FlightGear-прогон выполнен 2026-11-10 на macOS 26.5.1
(25F80), arm64. FG, SimGear и FGData — 2024.1.7, FG revision
`7241807173248abd838e2ab11337fbc5b2ae20b0`. Продолжительность **205.15 s
симуляционного времени / 223.23 s wall time**, 201 выборка, exit code 0.
В принятом прогоне нет сообщений solver/trim/Nasal failure, NaN или падения.
Это автоматизированный эксперимент в настоящем FG, не заявление о выполнении
всего маршрута человеком. Дополнительно в отдельном запуске визуально
проверены кабина, собственная геометрия, внешняя камера и переключение `v`:
[`cockpit.png`](fdm_lab_evidence/cockpit.png),
[`exterior.png`](fdm_lab_evidence/exterior.png). Скриншоты подтверждают вид,
а численный результат полёта подтверждается отдельной телеметрией.

В текстовых native-выводах удалены только пробелы в концах строк;
численные значения и сообщения сохранены.

В логах также остались диагностические сообщения установки: отсутствие
звукового файла (звук выключен), запрос throttle[0] при 0 штатных двигателей
и `Failed to save initial FDM property state`. Последнее относится к
`FDMShell::doInitAndBind()`/`copyProperties` при сохранении снимка для reset,
а не к solver или интегрированию; поэтому повторный Reset не заявляется.
Эти сообщения сохранены в excerpt, не замаскированы как чистая приёмка.

Проверки: `python3 tools/test_sa_fdm_lab.py` — 9 тестов; полный
`python -m unittest discover -s tools -p 'test_*.py'` — 98/98 на Python 3.11.6
в отдельном временном venv с зависимостями `requirements-dev.txt`.
Для loopback TLS-тестов потребовалось разрешить локальные сокеты за пределами
песочницы. Целевая CI-версия Python 3.14 здесь не запускалась. Никаких
модификаций общего workflow или чужих модулей для прохождения тестов нет.

Заявленный режим ограничен спокойной атмосферой, стартом в воздухе на 1000 m
MSL в указанной точке, скоростью до 25 m/s, малым креном/тангажом, помощниками
включёнными и небольшими перестановками высоты (+50 ft). Проверка завершения
требует ≥205 s, конечную скорость ≤0.5 m/s, ошибку высоты ≤0.5 m и дистанцию
до старта ≤10 m; в течение опыта h=995..1020 m, |roll|≤20°, |pitch|≤15°,
AGL>100 m и конечные числовые значения. Более широкий предел 45 m/s в
автоматической защите — аварийный порог, а не проверенный рабочий диапазон.

Не проверены: сильный ветер/турбулентность, большие углы, отказ стабилизации,
старт/посадка на опоры, произвольная масса, расход энергии, бой/MP, другие ОС,
вакуум/орбиты/точный канон. Гравитация и обратная связь активны: это не
`flight-model=null` и не зафиксированная траектория. Статические тесты
проверяют ресурсы/конфигурацию/целостность телеметрии и **не доказывают
аэродинамическую устойчивость**. Даже положительный опыт относится только
к этому режиму с вымышленными помощниками; ведущий принимает go/no-go.
