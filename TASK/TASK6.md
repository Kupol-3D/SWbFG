# TASK6 — Первый GUI клиента: профиль → фракция → корабль → запуск

**Срок:** 2–3 рабочих дня. Ветка `feat/task6-client-ui`.
Вход: `docs/TEAM_INTERFACES.md`, `tools/launch.py`, `client/`, существующие
тесты launcher. Эти файлы не дают готового API для выбора нового самолёта.

## Цель
Рабочий внешний экран клиента, а не только команда или макет: профиль
подключения, команда, корабль, кнопка «Вылет», понятные ошибки.
Выбор делаем ДО запуска FG: смена aircraft внутри процесса — отдельный риск.

## Выход
- Изолированный модуль `client/space_ui/`, инструкция и тесты
  `tools/test_space_ui.py`. Выбрать простой desktop-toolkit и описать
  зависимости; не добавлять тяжёлый стек только ради одной формы.
- Стилизованная, но читаемая форма: endpoint/callsign, Rebels/Empire,
  доступные/заблокированные корабли. Использовать демонстрационный каталог,
  явно пометить его; не писать «соединение защищено» до реального handshake.
- Mock-адаптер (авторизация/каталог/право вылета) и реальный безопасный
  запуск штатного c172p в solo. Это проверка запуска, не подмена X-wing
  самолётом c172p в интерфейсе. Дочерний процесс через argv, без shell.
- Интерфейс будущего relay-адаптера: preparing/connecting/ready/error;
  relay пока unavailable с понятной причиной. Токены не в argv/URL/репо.
  UI не выдаёт сам себе слоты и не считает server-ready по одному ping.

## Готово, когда
На основной доступной ОС кнопка запускает реальный FG/c172p; ошибки пути,
профиля и повторное нажатие обработаны. Есть скрин формы и тесты mock-flow/
argv. Windows/Linux записать отдельными строками tested/not-tested;
не требовать от одного человека двух проверенных сборок за три дня.

## Границы
Не менять `tools/launch.py` и старые профили: при нехватке его API предложить
маленький адаптер в своём модуле, общую правку интегрирует ведущий.
Без игрового Nasal, server protocol, нового транспорта, автообновления,
готового installer/EXE или утверждения о завершённой кнопке входа на VPS.
