# Командная работа

Один разработчик — свой клон; одна задача — ветка `feat/*`, `fix/*` или `art/*`.
Основная ветка `main`, изменения принимаются через PR с ревью.

```sh
git status
git switch main
git pull --ff-only origin main
git switch -c feat/task-short-name
# Выполнить задачу и проверки, затем добавить конкретные файлы:
git add path/to/file
git diff --cached
git diff --cached --check
git commit -m "Describe the change"
git push -u origin feat/task-short-name
```

Перед переключением веток сохранить свои незакоммиченные изменения.
Не использовать force-push/reset --hard для обхода непонятной ошибки.

## В PR

- Ссылка на TASK, результат и затронутые пути.
- Точные команды тестов, версия FG/ОС при runtime-проверке.
- Для моделей/UI — скриншоты; для FDM/сети — воспроизводимые логи/сценарии.
- Отдельно **не проверено** и известные ограничения.

Статика, Python, loopback TLS, FGMS и реальные FlightGear-клиенты — разные
уровни приёмки. Mock не подтверждает работоспособность сервера/симулятора.
Общие контракты и чужие модули менять отдельной согласованной правкой.

## Чистота и безопасность

Не коммитить ключи, токены, `.env`, личные адреса/профили, переписки, агентские
журналы, установленный FlightGear и результаты сборки. Данные для примеров —
localhost или зарезервированные example-домены, без действующих секретов.
`.gitignore` не удаляет уже отслеживаемый файл и не очищает историю.

Личные заметки/сессии/эксперименты хранить **вне корня репозитория**.
Командные решения и контракты — в `docs/`, результат задачи — в PR.
Общая инструкция агенту `AGENTS.md` допустима; локальные конфиги/истории
инструментов не являются общими исходниками.

`vendor/bombable` не форматировать и не редактировать. Изменения зависимости
делать отдельно с явным обновлением источника/хешей и соблюдением лицензии.
Собственные ассеты сопровождать автором, источником и разрешением; не брать
извлечённые ресурсы коммерческих игр. Приватность не заменяет лицензию.
