# Match core — контракт v1

Детерминированная **offline-библиотека**, не сервер и не публичный wire protocol.
Она не открывает сокеты, не запускает FG, не читает clock/random/файлы и не
вычисляет попадания. Одинаковые начальные данные и упорядоченные события
дают одинаковый результат. Порядок доставки задаёт будущий авторитетный адаптер.

## Идентичность и доверие

- `match_id` относится к одному раунду и не должен повторно использоваться
  для другого. Глобальную уникальность и storage обеспечивает интегратор.
- `player_id` — стабильная identity, не callsign и не номер MP-объекта.
  Reconnect/новый callsign не создаёт игрока и не возвращает корабли.
- `spawn_id` уникален за матч, включая уже завершённые появления.
- `event_id` идентифицирует одно событие. Повтор принятого события не
  применяется; тот же ID с другим содержимым — конфликт.
- Вход reducer — **доверенные, последовательно применяемые события**.
  Библиотека не удостоверяет, кто их отправил. Адаптер обязан привязать
  запросы к authenticated identity, а смерть подтвердить вне клиента.
  Проверка полей не превращает произвольный hit/death claim в достоверный.

## Состояние и переход

Базовые функции: `create_match(...)` и `apply_event(state, event)`.
Состояние JSON-совместимо, результат перехода содержит `state`, `accepted`
и машинный `reason`. Входные config/state/event не изменяются; возвращаемое
состояние не должно разделять изменяемые вложенные данные с ними.

Интегратор применяет события последовательно к последнему принятому состоянию
и атомарно сохраняет результат. Два вызова с одним старым state — две независимые
ветви вычисления, а не автоматическая блокировка/транзакция. Нельзя выдать два
spawn admission на основании конкурирующих результатов без сериализации/CAS.

Фазы: `lobby → running → ended`. Создание следующего матча — отдельный
`create_match` с новым ID, не сброс старого состояния по клиентскому запросу.
Завершённое состояние доступно для чтения, но новых игровых переходов нет.

Каталог задаёт конкретные типы отдельно для `rebels`/`empire`. Глобальный
каталог GUI, модель FG и сетевой callsign не загружаются библиотекой сами.
Команда фиксируется при join, состав — при start. Новые участники после
start не входят в этот раунд; повторный join не создаёт второй набор жизней.

## События

Общие поля: `version: 1`, `match_id`, `event_id`, `type`.
Неизвестные поля/типы и неверные значения отвергаются; никакого исполнения
кода из JSON и неявного приведения строк/boolean к числам.

| type | Дополнительные поля | Смысл |
|---|---|---|
| `join` | `player_id`, `team_id`, `callsign` | Вступить в lobby один раз |
| `start` | нет | Зафиксировать состав и начать раунд |
| `reconnect` | `player_id`, `callsign` | Обновить display-name существующего игрока |
| `spawn` | `player_id`, `ship_id`, `spawn_id` | Потратить слот конкретного типа |
| `death` | `victim_spawn_id`, `killer_spawn_id` | Подтверждённое уничтожение врагом |
| `crash` | `spawn_id` | Потерять свой аппарат без kill-point |
| `tick` | `elapsed_seconds` | Целое прошедшее время от начала раунда |

Callsign соответствует политике проекта: 1–6 ASCII букв/цифр, без `obs`-
prefix, уникален без учёта регистра. Вызов reconnect не является сетевым
handshake и не доказывает право на чужой `player_id`.

### Примеры входа

```json
{"version":1,"match_id":"round-1","event_id":"join-a","type":"join","player_id":"pilot-a","team_id":"rebels","callsign":"RED001"}
```

```json
{"version":1,"match_id":"round-1","event_id":"spawn-a","type":"spawn","player_id":"pilot-a","ship_id":"xwing","spawn_id":"spawn-a-1"}
```

```json
{"version":1,"match_id":"round-1","event_id":"death-b","type":"death","victim_spawn_id":"spawn-b-1","killer_spawn_id":"spawn-a-1"}
```

Это примеры формата: start, второй игрок и его spawn должны быть применены
раньше соответствующего death. Отдельный JSON не создаёт отсутствующий мир.

## Жизни, смерть и очки

Один активный аппарат на игрока. Первое появление сразу расходует слот типа;
посадка/смена callsign/reconnect не пополняют его. Новый `spawn_id` не
обходит потраченный тип, а повтор старого ID не создаёт новую жизнь.

Death допустим только для текущего живого victim spawn и текущего живого
killer spawn другой фракции. Он завершает victim spawn и добавляет ровно
одно очко команде killer. Повтор с новым event ID тоже отвергается.
Friendly fire/self-kill не меняют HP/жизнь/счёт; авария оформляется `crash`.
У `crash` нет поля отправителя: это уже подтверждённое authority закрытие
конкретного spawn, а не право клиента выбрать чужой аппарат. Проверку
собственности и причины аварии выполняет входной адаптер до вызова reducer.

**Ограничение v1:** posthumous kill от уже завершённого killer spawn не
поддерживается. Для снарядов/импульсов в полёте потребуется отдельный контракт
подтверждения; нельзя просто принимать старый spawn от клиента как доказательство.
HP, геометрия попаданий, ассисты и проверка реальной уничтоженности — вне ядра.

## Окончание и время

Default `target_kills=15`, цель не меняется под число игроков автоматически.
Первое достижение цели завершает матч немедленно; следующие события не
дают 16-е очко. Победа по цели имеет приоритет над исчерпанием в том же переходе.

Fallback — явная конфигурация, а не скрытый новый режим:
- `exhaustion_enabled=False` по умолчанию; при включении ноль неиспользованных
  слотов **и** живых активных кораблей команды означает её поражение.
- `time_limit_seconds=None` по умолчанию; положительный лимит проверяется
  по монотонному `tick.elapsed_seconds`. При лимите сравниваются очки,
  равенство даёт ничью, а не случайного победителя.

При 4×4 и трёх типах на пилота доступны лишь 12 потерь на сторону. Start с
целью 15 без обоих fallback должен отказаться с `unreachable_target`;
с явно включённым fallback он допустим и завершается по отдельной причине.
Начального достаточного бюджета всё равно недостаточно для гарантии 15
после аварий: для практического матча следует согласовать fallback заранее.

Tick — вход авторитетного таймера, не время клиентского компьютера. Ядро не
переупорядочивает одновременные события и не является distributed consensus.
Batch одновременных смертей требует отдельной версии/политики, если понадобится.

## Восстановление и интеграционные границы

API: `snapshot(state) → dict`, `restore_snapshot(payload) → state`.
Envelope содержит ровно два поля:

```json
{
  "version": 1,
  "state": {
    "version": 1,
    "match_id": "round-1",
    "phase": "lobby",
    "config": {
      "target_kills": 15,
      "exhaustion_enabled": false,
      "time_limit_seconds": null
    },
    "catalog": {"rebels": ["xwing"], "empire": ["tie"]},
    "players": {},
    "spawns": {},
    "scores": {"rebels": 0, "empire": 0},
    "clock": {"elapsed_seconds": 0},
    "seq": 0,
    "history": [],
    "event_ledger": {},
    "result": null
  }
}
```

Это полный пример пустого lobby, не начавшийся матч 1×1 до 15 очков.
DTO активного матча создаётся функцией `snapshot`, не ручным набором полей.
История — упорядоченный массив, каждая принятая запись сохраняет исходное
нормализованное событие, sequence, ID, тип и fingerprint. При восстановлении
события переигрываются из начальной конфигурации; итог точно сверяется с
кешированным состоянием. Повреждённый snapshot отвергается, не «чинится».

Snapshot должен сохранять команду, потраченные типы, активные/закрытые spawn,
счёт/время/исход и защиту от повторных ID. JSON encoding/storage выполняются
вызывающим кодом; библиотека не пишет файл и не выбирает личный каталог.
Структурная валидация snapshot не доказывает его происхождение: принимать
состояние можно только из доверенного авторитетного storage, не от игрока.
Дедупликация и порядок принятых событий должны переживать JSON roundtrip;
порядок ключей JSON-объекта не используется как порядок событий.

Отдельные следующие задачи:
- runtime-место исполнения, authenticated event ingress и доставка snapshot;
- атомарное хранение/восстановление последнего принятого состояния;
- reserve/admit/launch-confirm и rollback неудачного старта FG;
- disconnect/grace/abandon и выдача прав новому матчу;
- доказательство попаданий/уничтожения и дополнительные игровые правила.

Без этих компонентов бюджет остаётся корректной offline-моделью, а не
серверным принуждением или античитом в настоящем FlightGear.
